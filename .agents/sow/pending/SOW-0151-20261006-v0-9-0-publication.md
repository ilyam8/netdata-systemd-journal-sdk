### Assistant Understanding

Facts:

- SOW-0150 prepared versions, install guidance and migration notes in PR #6.
- The Go module path is `github.com/netdata/systemd-journal-sdk/go`; root
  `v0.9.0` and `go/v0.9.0` must peel to the same merged release commit.
- On 2026-10-06 the crates.io owner list for all eight `systemd-journal-sdk*`
  crates contained only user `ktsaou`. Publishing requires that owner, or an
  owner or team he adds, plus a Rust toolchain and a crates.io API token.
- In the preparation clone, `origin` is the user's fork and `upstream` is
  `netdata/systemd-journal-sdk`. The release-tagging skill's `origin` means
  the canonical repository.

Inferences:

- Rust crates should be published before tags are pushed, matching SOW-0117,
  so a partial Rust failure does not leave Go tags announcing an incomplete
  release.

Unknowns:

  crates.io lookup.
- Annotated `v0.9.0` and `go/v0.9.0` exist on `netdata/systemd-journal-sdk`
  and both peel to the PR #6 merge commit; verified with `git ls-remote`.
- `go list -m github.com/netdata/systemd-journal-sdk/go@v0.9.0` resolves.
- A fresh Rust consumer resolves `systemd-journal-sdk = "0.9.0"`.

Failure handling:

- Run every remote tag check and tag push against the canonical repository
  (`upstream` in a fork clone), never the fork. If a release tag reaches the
  fork by mistake, report it to the user before taking corrective action.

  partial publication, and do not push tags until resolved.
- If `v0.9.0` or `go/v0.9.0` already exists at another commit, stop and ask the
  user. Never move, delete or force-push release tags without approval.
