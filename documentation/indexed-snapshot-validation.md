# Indexed snapshot implementation evidence

The source adds native-index snapshots and explicit strict verification in Go and
Rust. This is SDK evidence; DEM adoption and published dependency validation are
separate work. Measurements used synthetic files on macOS arm64 (Apple M4 Pro),
Go 1.27.1 and Rust 1.91. No OS cache flush was performed.

## Correctness and interoperability

- Full Go module tests and vet pass. The full journal race suite passes; focused
  snapshot/verification race tests also pass after the final capture checks.
- Rust core: 81 tests; directory writer: 9; public SDK: 142. Two existing macOS
  group-name tests expect `root` where the host resolves `wheel`; both failures
  were reproduced on the unchanged baseline and excluded from the focused run.
- The Rust shared conformance adapter passes all 15 scenarios. Both languages
  read historical systemd whole-file compressed fixtures and test regular/
  compact layouts, all DATA compression modes, binary fields and multivalue
  posting multiplicity.
- Concurrent append tests preserve the frozen population while old DATA gains
  its first posting array or extends existing arrays. Tiny reader windows force
  remapping during payload callbacks. Capture/global traversal remains strict;
  query-time clipping tolerates unpublished future slots only under the valid
  graph and append-only preconditions.
- Writer faults reproduce failed first-append cleanup, sync and archive failures;
  strict verification rejects interrupted publication and missing reverse links.
  Input validation errors before mutation remain reusable.
- All 33 wiki examples compile/run; wiki structure and 78 documentation harness
  tests pass.
- Stock `journalctl` 257.13 verifies all seven Go/Rust journals generated by the
  documentation harness. This used a disposable container with read-only
  synthetic fixtures, not the host journal. It is closed-file validation, not a
  claim of a newly run Linux live-reader matrix.

## Query cost

`BenchmarkIndexedSnapshot` uses 100,000 rows, three fields, 1,000 bucket values
and deliberately small test hash tables (64 DATA buckets). Results include open
and close; query callbacks visit payloads. Medians over six runs:

| Operation | Time | Allocated bytes |
|---|---:|---:|
| Snapshot capture | 28.1 us | 12,344 |
| Exact bucket, 100 rows | 205 us | 12,456 |
| FIELD selection, same 100 rows | 392.5 us | 12,440 |
| All 100,000 rows and payloads | 13.31 ms | 12,608 |
| Existing eager reader open alone | 2.195 ms | 5,155,297 |

This isolates capture/selection cost, not a DEM reducer or a production latency
budget. Small collision-heavy tables are intentional; production hash sizing
and cardinality change exact-lookup costs. Broad traversal still does O(rows)
work. Whole-file compressed inputs retain staging costs.

A separate Go-generated mixed 250,000-row fixture from the history-time spike
was read by Rust's public example: capture 97 us, exact 2,496 metadata visits
265 us, FIELD selection 2.645 ms, and global 250,000 metadata visits 10.949 ms.
These callbacks do less work than the Go payload benchmark; do not interpret
the numbers as a language speed comparison.

## Strict verification and writes

On that mixed fixture, Go strict verification took 1.04 s with 681.6 MB of
cumulative allocations and about 494 MB process-tree peak RSS. Rust took 1.64 s
with about 537 MB child peak RSS. RSS includes runtime/mapped memory, not just
retained heap. Both verifiers have graph-sized memory costs. The previous Go
compatibility-verifier trial was interrupted after 152 s without finishing the
first file; that is an aborted probe, not a measured completion time.

Go repeated-value strict-verifier benchmarks at 1k/10k/100k rows took about
1.03/4.69/39.68 ms, consistent with linear posting work. Strict verification is
for offline recovery, not every query open. Selective startup verification of
uncertain active files is a consumer policy, conditional on finalized archive
provenance; schema coverage alone does not establish integrity.

Six alternating 30,000-row mixed/32-field structured Go writer trials gave
median append times of 143.3 ms before and 146.2 ms after the lifecycle fix
(about 2.0%, overlapping ranges). These trials do not establish a broad
performance regression or improvement. Successful writes retain the same
format/publication path; failure handling adds the failed-state guard.

## Independent review close-out

Two independent reviewers assessed Go index/lifecycle behavior and Rust/parity.
Review fixes in `cd0dfaf` enforce Go FIELD chain order, gate historical tail boot/
monotonic comparisons on the format compatibility flag, and require Rust hash
tables to belong to the committed object graph. A matching Go FIELD with no DATA
head now errors rather than reporting absence. Each correction has a regression
that failed before the source fix. Both reviewers confirmed the corrections;
no verified blocker remains in their scopes.

The final focused Go race checks pass; the final Rust public suite passes 142
tests with the two baseline platform exceptions above. Both public APIs also
strictly verify and perform exact/FIELD/global traversal on all seven Go/Rust
documentation writer fixtures. No Linux live-reader result is inferred from this
closed-file evidence.
